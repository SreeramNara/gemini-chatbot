Developing your service

Cloud Run services must follow specific runtime rules.

Code requirements

Your service must:

Listen on the PORT environment variable
Be stateless
Not depend on local persistent storage
Support concurrent requests
Background processing rules

If your service runs background tasks:

Must use instance-based billing
Otherwise CPU may not be allocated outside request handling
File system limitations
NFS support requires second-generation execution environment
Programming language support

Supported via buildpacks
Node.js
Python

Java
Custom support
Any language works if packaged as an OCI-compliant container
Using a web server

You can use standard web frameworks:

Node.js → Express
Python → Flask
Ruby → Sinatra

Containerizing your code
Dockerfile

A Dockerfile defines how your container is built.

Key points:

Starts from a base image (FROM node, FROM golang, etc.)
Installs dependencies
Runs on Linux x86_64 ABI

Example system package installation:

RUN apt-get update -y && apt-get install -y \
  graphviz \
  && apt-get clean
Buildpacks

Instead of Dockerfiles:

Cloud Run can build automatically from source
No manual container setup required

Use this when:

You want simpler deployments
You use supported runtimes

Cloud Run Functions Overview

This guide provides an introductory overview of how other Google Cloud services are involved in the Cloud Run functions deployment process.

Before You Begin

Familiarize yourself with Cloud Run functions and source deployment concepts from the Cloud Run deployment options and resource model guide.

Architecture Overview

When you deploy your function's source code to Cloud Run functions:

Your source code is stored in a Cloud Storage bucket.
Cloud Build automatically builds it into a container image.
The container image is pushed to Artifact Registry.
Cloud Run functions pulls this image when executing your function.
Deployment Flow
Source Code → Cloud Storage Bucket
Cloud Build → Container Image
Artifact Registry → Image Storage
Cloud Run → Runs the Service
API-Based Behavior
If using Cloud Run Admin API (Recommended)
Source code uploaded to Cloud Storage bucket (no retention period)
Bucket name format:
Default encryption:
run-sources-PROJECT_ID-REGION
CMEK encryption: user-provided bucket name
Cloud Build:
Uses buildpacks + Functions Framework
Creates container image
Uses e2-standard-2 machine type

Image stored in:

REGION-docker.pkg.dev/PROJECT_ID/cloud-run-source-deploy
Image deployed to Cloud Run as a service
Trigger options:
Eventarc
Pub/Sub
HTTP triggers
If using Cloud Functions API (v2)
Source uploaded to Cloud Storage bucket:

Default encryption:

gcf-v2-sources-PROJECT_NUMBER-REGION

CMEK encryption:

gcf-sources-PROJECT_NUMBER-REGION-CMEK_KEY_HASH
Cloud Build:
Uses buildpacks + Functions Framework
Uses e2-standard-2

Image stored in:

REGION-docker.pkg.dev/PROJECT_ID/gcf-artifacts
Deployed to Cloud Run as a service
Trigger options:
Eventarc
Pub/Sub
HTTP triggers
Compare Cloud Run Functions
Overview

There are two versions:

Cloud Run Functions (Latest)
Built on Cloud Run services
Created using:
Cloud Run Admin API (recommended)
Cloud Functions v2 API
Cloud Run Functions (1st Gen)
Original Cloud Functions system
Limited triggers and configurability
Runs on Google internal infrastructure
Concepts Comparison
Resource Model
Latest: Function = Cloud Run service from source code
1st Gen: Function deployed directly from source
Function Types
Latest:
HTTP functions
CloudEvents (event-driven)
1st Gen:
HTTP functions
Limited event-driven support (runtime dependent)
Image Registry
Latest: Artifact Registry only
1st Gen: Artifact Registry or Container Registry (deprecated)
Pricing
Latest: Cloud Run pricing
1st Gen: Legacy pricing model
Configuration Differences
Feature	Cloud Run Functions	1st Gen
Timeout	Up to 60 min (HTTP), 9 min (events via v2)	9 min
Memory	Up to 16 GiB	Up to 8 GiB
CPU	Up to 4 vCPU	Up to 2 vCPU
Concurrency	Up to 1000 requests	1 request
Traffic splitting	Supported	Not supported

Functions Framework Overview

Cloud Run functions use the Functions Framework:

It allows you to:

Run HTTP functions
Handle CloudEvents
Test locally
Function Structure

A function requires:

1. Entry Point

This is the function that executes when triggered.

2. Signature Type
HTTP function
Event-driven (CloudEvent)
Source Directory Structure (Node.js Example)
.
├── index.js
└── package.json
package.json Example
{
  "main": "index.js",
  "dependencies": {
    "@google-cloud/functions-framework": "^3.0.0"
  },
  "type": "module"
}
HTTP Function Example (Node.js)
import { http } from '@google-cloud/functions-framework';

http('myHttpFunction', (req, res) => {
  res.send('OK');
});
Event-Driven Function Example
import { cloudEvent } from "@google-cloud/functions-framework";

cloudEvent('myCloudEventFunction', event => {
  console.log(event.data);
});
